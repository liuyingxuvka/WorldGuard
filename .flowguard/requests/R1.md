# WorldGuard 方案清单（第十一轮：第 0 阶段 0.7.24 → 0.8.0；第 3 阶段 0.8.0 → 0.8.1）

## 这份清单要达到什么（方案总览）

WorldGuard 补的是 AI 写故事、行程和计划时的弱点：前后矛盾、人不在场却做了事、东西已经给了别人还在用。AI 把世界写成一个小的可执行模型，每条说法用 `claim.asserts` 绑到模型上，由工具检查。第十一轮的试验（灯塔钥匙，两章；规划阶段证据（不在包里）：findings/skills11-pw.md §1.4，W1–W5）说明了它在哪里有用、在哪里没用（设计说明 §4 开头）：

- **有用的地方，都是工具在做 AI 容易错的那一步。** 按时间重放事件、查前提、把前一章的结束状态交给下一章。
- **没用的地方，都是同一个 AI 既写说法又写检查。** W3：AI 把“Lena 开门”只写成要求 `door_locked`，没写要求她拿着钥匙、在岛上，检查就重复了 AI 的错，`PASS`；W3 里测试者自己写的变体也同样漏掉。

所以第 0 阶段把剩下的“AI 自己写的步骤”交给工具，或者让它对上一份 AI 没在同一口气里写的记录；不加新的模型种类（设计说明 §4.3）。

### 0.5 路线（旧模型 → 目标模型 → 代码）

FlowGuard v0.71.0 的路线和 v0.70.14 一样，多了几步（FG 清单 §0.1 的表）。本清单用到的写在这里：

**路线 (b) 目标。** 改任何模型文件（规则、已知坏、conformance、`TESTED_BY`、`IMPLEMENTED_BY`、`USES` 等），加或删模型文件，或改地图结构，都走这条。`.flowguard/models/` 里的当前模型从不原地改。

1. 上一个条目推送后的 CI 是绿的（`gh run list --branch main --limit 1`）。红的先修：单独提交 `<编号>: Fix <问题>`。
2. 先定位：`python -m flowguard read --find <路径:函数>`，只打开它指出的模型。条目写的模型就是规划阶段在 v0.7.24 上 `read --find` 的结果；不同就记进日志，照 `read --find` 做。
3. 【目标开始】；对条目点名的每个模型各做一次【加入目标】。下划线开头的帮手文件（`_world_fixture.py`）没有 id：要改它就 `cp .flowguard/models/_world_fixture.py .flowguard/target/models/` 再改副本。
4. 只改 `.flowguard/target/` 里的副本。
5. 【设计检查】：先修掉每个 `ERROR`；再看缺口行，原样抄进日志。新加的规则写代码之前打印 `EXPECTED GAP <模型>: ...`。例外：`no rule change`、`moved rules only`；新规则打印 `NO GAP`（只记录今天已有的行为：不为它写代码，提交信息正文写 `records existing behaviour: <规则名>`）。**改了的**规则打印 `NO GAP` 时是 TO-DO `rule_changed_without_line`：照 0.7 在 `.flowguard/target/changes.txt` 写一行。
6. `git add .flowguard/target && git commit -m "<编号>: target"`。这个提交只含 `.flowguard/target/`，先不推送。
7. 改代码、加测试；【设计检查】想跑几次就跑几次，直到没有 `TO-DO`（写了代码以后是 `GAP CLOSED <模型>: ...`）。
8. 【提升】。它最后打印主人块：原样贴进日志。成功以后运行它打印的 `python -m flowguard map confirm <ids>`（先读每个组件的描述，行为变了就改）。
9. 照提升最后一行暂存：`git add -A .flowguard <本条目改的代码、测试、文档路径>`（删掉的 `.flowguard/target/` 也进这个提交）；`python -m flowguard map check --strict | tail -1` 干净；第二个提交；两个提交一起推送。

**路线 (a0) 只改代码、测试或文字。** 所有模型文件和地图结构都不变。行为变了先写一个在旧代码上失败的测试，再改代码；【变更】；读它点名的过时组件的描述，行为变了就改；运行它打印的 `map confirm`；提交；推送。这条路线上有模型文件要改就是走错了：`target add` 它，改走 (b)。

**设置直接改。** `accepted_debts`、`ignore`、`import_roots`、`large_model_seconds`、`large_test_seconds`、`test_commands` 和组件的 `tests` 列表是设置：直接改 `.flowguard/map.json`，改前改后各跑一次【地图检查】，除了条目写明的变化不能多出别的发现。

**看到这些行要做什么**：照 FG 清单 §0.1 “看到这些行要做什么”（`next[<编号>]:`、`debt_without_expiry`、`debt_expired`、`target_already_promoted`、`target_deleted_not_staged`、`model_edited_outside_target`、`owner_text_edited`、`rule_changed_without_line`、`quote_not_in_request`、`link_without_shared_term`）。

**每个条目推送以后**跑【历史检查】。

### 0.10 数字和卡住怎么办

- **数字**（主人的说明 H）：没有一个尺寸数字或秒数是通过不通过的标准，条目、第 5 节的行和你新加的测试都不用它们。秒数和字符数写成“规划阶段实测”或写进成本表，只作报告；一条路径变慢了、一段输出变长了，不算失败：在成本表的“差别去了哪里”一列写明多出来的去了哪里。仍然是数字的只有已经强制的拆分触发（每个模型 8/12 条规则、2,000/10,000 个探索序列，每个测试文件 40/60 个测试函数），本清单给模型加规则时都算过（第 4.2 节）。
- 验证结果和清单不符：照 `00_先读我.md` 的“卡住怎么办”。撤掉没提交的改动用 `git restore --staged --worktree .`，新文件用 `git clean -fd -- <路径>`，放弃一个目标用 `python -m flowguard target drop --yes`。
- **按定义判断，不按预计行**：条目里新建的信息原文是要求，必须一字不差；规划阶段对旧行的预计（某条命令打印几行、某个模型多几个用例）对不上时，按条目写的定义判断，把预计、实际和依据写进日志。
- 不放松、不删已有的功能断言；不删用例或已知坏。WG-604 必须换掉三个已知坏的改法（例子、参考和一个测试里的变体），原因和新的改法都写在那个条目里；除此以外不改任何已知坏。
- **FlowGuard 的问题**：在 WorldGuard 里遇到 FlowGuard v0.71.0 或 v1.0.0 本身的问题，命令和完整输出记进 `../worklog_cross.md` 的 `## FlowGuard 问题`，按 `00_先读我.md` 的规矩处理；不在本仓库里写绕过 FlowGuard 的代码。
- **WorldGuard 代码上的发现在代码里修**（设计说明 §0.6）：FlowGuard 的检查（第 3 阶段的 `audit` 尤其如此）报出 WorldGuard 代码的真问题时，修代码，不接受、不记债；一个写明了该跑什么命令的拒绝算进展，不算卡住。
